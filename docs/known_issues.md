# 📋 Excel Tool Harness 已知问题与潜在风险清单 (Known Issues & Risks)

> 记录当前系统在架构、性能、安全及模型交互层面存在的客观局限与隐患，供后续阶段演进排期与重构修复。

---

## 1. 🛡️ 安全与沙箱隔离问题 (Security & Sandboxing)

### 1.1 宿主机进程级执行，缺乏容器内核级硬隔离
- **现状**：目前 Python 脚本通过 Node.js `child_process.spawn` 直接在宿主机环境中执行。虽然配置了 `input.json` 落盘、`OUTPUT_DIR` 隔离、原文件 SHA-256 篡改秒级自愈与两段式进程终止（SIGTERM -> SIGKILL），但其本质依然运行在宿主机操作系统上。
- **风险**：若发生恶意的 Prompt 注入或模型失控生成了破坏性指令（如 `os.system("rm -rf ~")`、遍历读取敏感目录、扫描内网或发起恶意网络攻击），宿主机系统面临安全风险。
- **演进建议**：未来若面向公开网络或多租户部署，应升级为 Docker 容器化沙箱、gVisor 轻量级隔离或 WASM (Pyodide) 纯前端无后端运行环境。

### 1.2 本地文件系统白名单的边界限制
- **现状**：Web 路由中通过 `isPathSafe` 限制只能访问 `.sessions/` 目录下的产物。
- **风险**：若用户通过自然语言指示模型读取本地其他任意路径的参考文件，或代码试图输出到非 `OUTPUT_DIR` 路径，可能导致读取失败或受限于当前白名单规则。

## 2. ⚡ 大文件与极端复杂表格性能瓶颈 (Performance & Memory)

### 2.1 真实运行期大内存消耗（OOM 隐患）
- **现状**：在代码生成预检阶段，系统已实现了超大文件自动抽取 80 行微样本（Micro-sample Slicing），将预检试跑压缩在毫秒级。但在右侧沙箱运行真实完整大文件时，脚本将加载全部真实数据。
- **风险**：对于数十万行、多 Sheet 或包含大量复杂样式的上百兆 Excel 文件，`openpyxl` 在非只读模式下的内存占用通常为原文件体积的 5~10 倍，容易导致宿主机 Python 进程内存暴涨甚至 OOM 崩溃。
- **演进建议**：推动超大文件场景强制走 Polars / DuckDB 或 `openpyxl(read_only=True)` / 分块流式（Chunked Streaming）处理范式。

### 2.2 前端可视化数据预览仅限前 15 行
- **现状**：`OutputPreviewModal.vue` 目前仅嗅探并展示产物前 15 行样例数据。
- **局限**：如果用户需要进行全量分页浏览、搜索特定行、或核验万行表末尾的汇总结果，目前必须点击下载到本地 Office 软件中打开。

## 3. 🤖 模型交互与代码生成局限 (Agent Loop & Code Generation)

### 3.1 单轮全量重写，缺乏增量 AST/Diff 编辑机制
- **现状**：用户在左侧对话中针对工具提出细微调整（如“把第三列列名改一下”或“增加按金额倒序排序”）时，Agent Loop 会命令大模型**全量重新生成**整段 Python 脚本与 UI Schema。
- **风险**：
  1. 消耗额外的 Token 开销与等待耗时；
  2. 对于 100 行以上的复杂处理脚本，全量重写有一定概率“按下葫芦浮起瓢”，导致上一轮已经调试验证正确的边界处理逻辑在重写时遗失。
- **演进建议**：引入类似于 Aider / Cursor 的增量代码块替换（Search & Replace Block）或基于 Python AST 的局部函数更新机制。

### 3.2 线性上下文膨胀与多轮遗忘
- **现状**：多轮修改时，会话历史按线性消息累积。若经过 5 轮以上的持续微调，Prompt 上下文会逐渐臃肿。
- **演进建议**：设计会话上下文压缩（Context Compaction），仅保留初始需求、最新版代码与最新报错修正记录。

## 4. 🏢 部署与生产工程完备度 (Deployment & Multi-tenancy)

### 4.1 本地单机文件存储架构
- **现状**：会话状态、用户上传文件、快照备份与中间产物均保存于本地磁盘 `.sessions/` 目录，元数据以本地 JSON 文件存储。
- **局限**：当前定位极佳地契合了本地专业个人工作站，但完全不具备多用户隔离、横向水平扩容、持久化数据库存储和分布式任务调度能力。
- **演进建议**：若后续商业化 SaaS 改造，需将本地文件存储解耦为 S3/OSS 对象存储，会话落入 PostgreSQL/MySQL，任务由 Redis/BullMQ 异步队列调度。

### 4.2 外部 Python 生态依赖
- **现状**：项目强依赖宿主机已安装 Python 3.10+ 以及 `pandas`、`openpyxl` 库。
- **局限**：对于不具备开发环境的普通小白用户，无法开箱即用，必须先配置 Python 环境及 pip 依赖。

---

## 5. 📊 Excel 特性与复杂生态天花板 (Excel Feature Limitations)

### 5.1 复杂公式与 VBA 宏的保全限制
- **现状**：尽管在 Playbook 中制定了诚实性准则，但在底层 openpyxl 生态中，对复杂透视表（Pivot Table）多维切片器、带密码保护的表格、以及动态数组溢出公式的处理仍存在客观生态天花板。
- **风险**：在遇到含有高级 VBA 宏工程的 `.xlsm` 文件时，代码读写可能会导致宏信息丢失。
